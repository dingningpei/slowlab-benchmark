# Phase 1：保温幕共同控制与天气协议暂停点

2026-09-27。**幕布接口缺口已修复；Phase 1 尚未完成，暂停在全年天气协议缺口。**

## 本轮实现

开发合同 `configs/v22/task_contract_v2.json` 从 v1 派生并保存前版哈希。保留原生幕布响应曲线和常数，改为共同控制器每300s基于最新已到达观测计算 `uThScr`，通过 `cmdScreen` 输入模型，期间不允许原生求解器重新决定实际幕布位置。

`slowlab/v22/controller.py` 只接收观测存储的查询结果，不接收模型状态/环境对象。检查测量与到达时间、有限值、单位和必需通道；缺失时失败，没有隐藏状态兜底。active 模式依据已提交处理的昼夜温度和RH目标；cleanup/idle 模式不使用旧处理，改用统一10°C供暖保护和87%幕布RH参考。87%及曲线常数来自原生规则，待机耦合属于开发假设。

同一固定时钟定义用于内外日夜标签（06:00–22:00）；在该开发版本将 isDay/isDaySmooth 同步保持为 cmdDay。这是共同底层控制的版本变化，不宣称与旧连续幕布路径产生相同物理轨迹。没有增加 LLM 可调幕布维度，也没有将幕布湿度响应等同雾化控制。

`ReusableGreenLight` 在 v2 合同下必须接收五个命令，漏传幕布会拒绝；旧合同保留四通道以复现历史。`CropLifecycle` 现在可显式选择缓存/编译后端，默认仍原路径。每步日志记录控制输入的测量/到达时间、请求和实现的执行器分数；温度等受控状态不保证达到目标值。当前理想执行器直接执行合法分数，不声称模拟了已校准执行延迟或故障。

## 验证范围

`results/v22/phase1_screen_controller_result.json`：两个独立传感器—控制器分支分别使用原生和编译求解器，601步，包含12步运行、576步完整清理、1步空置、重种和12步运行。全部状态最大差0；资源账在预设rtol=1e-5、atol=1e-9内一致。五个执行器每个步内严格等于请求值；幕布跨tick在约1e-22到0.00990099之间变化。清理未满拒绝重种；重种时非作物状态不变。总墙钟约51.69s，单线程。

89项相关轻量测试通过，包括未到达记录不能影响指令、到达后可影响、缺失观测拒绝、相同可见历史相同指令、待机不继承旧policy、幕布冷热湿边界及已有数值/生命周期测试。

固定天气仍为测试夹具；测试不是极端天气能力、成熟作物或全年有效性的证据。幕布输出覆盖范围较窄，日后仍须变化天气验证。Full/Endpoint代理权限、多隔间调度、年度守恒/收敛与最终结算仍未完成。

## 下一实质问题：365天活动没有已冻结天气协议

检查现有本地审计记录后，`results/v22/phase1_weather_contract_audit.json`记录：

- 原始GreenLight实验区间112天；
- AGC2023记录65天；
- AGC2024天气记录约80天。

这些只表示已审计来源的覆盖，不是对全部可用数据的穷尽搜索，不说明其他全年数据不存在。没有重新读取保留的结果值，也没有下载数据。2024记录仍遵守其原先证据角色，不因本次覆盖审计自动变成开发集。

当前机器合同没有全年天气源/生成器、起始季节、相关变量联合结构、缺失与时区规则、开发/试验/独立评测分区。现有适配器仍将室外天气固定为短测常数（包括夜间固定辐射）；不能把它投入正式全年活动。短季节记录反复循环、独立打乱温度/湿度/日照、将未来记录暴露给controller均不可接受。

建议下一步先做全年或多年连续气象数据的**元数据与规模可行性检查**，尽量复用现有本地材料；选定气候区域、时间语义、源变量与必要派生假设，冻结开发和独立评测分区。纯模拟论文的天气来自公共气象并不要求实体温室结果；但新天气实例的联合时序与盲测规则仍要明确。若需大型下载，先向用户说明体积并请求同意。

按“完成Phase1或遇到问题停下来”的要求，本轮暂停在这个会改变季节性、补光需求和能源评价的合同缺口，不用方便的拼接替代科学定义。未提交、推送、调用LLM API或运行大规模实验。
