# Phase 1：远程计算预检查（私有东京服务器）

日期：2026-09-28。只记录非敏感的资源与性能信息；不记录 IP、用户名、SSH 选项、密钥或账户资料。此文档可供下一位协作者判断远程 pilot 的可行性。

- Linux x86_64，2 个 vCPU / 1 个物理核心（超线程 2），总内存约 896 MB、无 swap；`/tmp` 所在盘检查时约 12 GB 可用。
- 系统默认 Python 3.6.8；另有 Python 3.11 和 GCC 10.2。已在服务器用户目录下建立隔离 Python 3.11 虚拟环境，安装锁定数值轮子：NumPy 1.26.4、SciPy 1.14.1、pandas 2.2.3、numexpr 2.10.1，以及 h5py 3.16.0。未更改系统 Python。
- 上传并校验约 254 KB 代码包；短程对照补入 v2 合同后 manifest 为 100 个文件，包括当前 SlowLab 数值代码和锁定 GreenLight 源码；不含 `.env`、密钥或 `reviews`。源码文件哈希清单在远程包内。
- 原生 RHS 原先把 `/usr/bin/clang` 写死，已改为明确选择本地 clang/GCC，保持 `-O2 -fno-fast-math -ffp-contract=off`，Linux 额外链接 libm。Mac 端原 600 步回归仍逐状态一致；服务器 GCC 通过 28 状态单步，模型加载约 12.2 秒，峰值内存约 116 MB。
- 不含天气与控制器的固定驱动 24 小时（288 个 300 秒步）在该服务器单 worker 用约 4.51 秒，RSS 约 118 MB。机械外推四隔间 365 天约 1.83 小时，旧 1,024 campaign 草案约 1,873 单 worker 小时；**这不是正式运行时间估计**，因缺少变化天气、成熟作物、观测历史、账本及模型加载。服务器能卸载 MacBook 的热负担，但现有规格不会自动让大矩阵快速结束。不能把 2 个超线程当作 2 个独立物理核心或假定可稳定运行多 worker。

用户已明确批准该天气产品传输。98 个 Cabauw lc1 文件（18,413,090 字节）及 manifest 已传至独立 pilot 目录；归档与逐文件 SHA-256 均通过。没有传输 `.env`、密钥或 `reviews`，也没有运行全年或 LLM 实验。

可复核的非敏感结果保存在 `results/v22/remote_reference_6step_result.json`、`results/v22/remote_native_6step_result.json`、`results/v22/remote_active_7d_array_result.json`、`results/v22/remote_active_7d_frame_result.json`、`results/v22/local_active_7d_array_result.json`、`results/v22/local_active_7d_actions.json` 和 `results/v22/remote_active_7d_fixed_actions_result.json`；天气原始文件仍在 Git 外。

同一服务器上，六个 300 秒天气步的参考求解器与 GCC 原生 RHS + 数组输出均通过；28 个末状态的最大绝对差为 `7.23e-10`，账本最大绝对差为 `8.53e-14`。控制指令仅出现浮点末位差异。由此可以排除一个明显的短程 GCC 实现错误，但不能证明全年数值稳定。

七天早期活跃作物窗口（单隔间，2,016 步）在服务器上运行两次：数组输出总计 49.80 秒、步进 37.27 秒、Linux 峰值 RSS 约 130 MiB；DataFrame 输出总计 55.45 秒、步进 43.44 秒，**同服务器两条路径的 28 个末状态及资源账逐值一致**。Mac 同窗数组输出步进 8.24 秒，因此这台服务器单 worker 约慢 4.5 倍，作用是卸载 MacBook 风扇/热负担，而非加速大矩阵。

Mac 与服务器七天闭环输出并非逐值一致：28 个状态中最大相对差约 `1.59e-4`（土壤温度），供暖账相对差约 `0.175%`。六步参考路径跨平台在 `1e-8` 相对/绝对阈值下相同，且服务器内部七天两种输出完全一致。逐步比较五个控制通道发现，2,016 步中有 77 步至少一个命令相差超过 `0.01`，第一处超过该阈值在第 1,320 步；最大差达到 1.0（供暖命令）。

将 Mac 的 2,016 条控制命令固定回放在服务器的同一天气窗口后，供暖账与 Mac **逐值相同**，28 个末状态最大相对差约 `2.33e-11`。这说明观察到的七天偏差主要通过闭环控制放大；最初微小数值差的具体平台来源尚未定位，不能单凭这项诊断归因于 GCC 或 SciPy。正式比较应固定同一运行镜像/数值栈，并预先规定数值容差、控制决策边界与主要结果敏感性检查。这个 fixed-action 回放只是数值诊断，不是正式实验臂。

仅按七天早期作物步进线性外推，四隔间全年约 `37.27×365/7×4≈7,773` 秒（约 2.16 单 worker 小时）。这项旧外推已被下面的单隔间全年实测替代，仍不能推断四间并行内存。

## 全年单隔间 pilot 的资源故障（持续审计）

按合同 v3 的固定策略，在 2017 年天气下计划运行 365 天、两轮各 180 天作物、每轮后 2 天清理、最后 1 天 idle。脚本 `scripts/v22/check_annual_runtime_pilot.py` 逐日写入进度，内层检查时间和 RSS，外层强制 3 小时停止；这是运行成本与跨生命周期稳定性 pilot，不是正式 agent 实验。

- 第一次使用 `prlimit --as=600000000`（虚拟地址空间）限制，在第 59 天后 Python 收到 SIGSEGV，退出 139；末次记录 RSS 约 189 MB。后续运行第 65 天的虚拟地址空间达到约 607 MB 仍继续，强烈支持第一次的地址空间限制过严，但没有核心堆栈可以完全证明直接原因。
- 第二次改用 systemd cgroup 的 600,000,000 字节实际内存上限，顺利通过第 180 天停种、两天清理和再种；到第 290 天后退出 137。内核记录为**全局 OOM**，不是 cgroup 限额事件；进程末次逐日 RSS 约 388 MB，主机只有约 896 MB RAM、无 swap，其他服务同时占用内存。没有把这次中断解释为物理模型失败。
- `OnlineObservations` 原先同时保存按通道排序的记录与全局 identity 字典。已改为在按通道时间索引中检测重复，并给不可变记录使用 slots；乱序交付/重复 identity 的回归测试通过。Mac 上独立构造 200,000 条记录的峰值 RSS 从约 109 MB 降至约 66 MB。东京同一天前缀动态运行的末状态和资源账与修改前逐值相同。

第三次使用更保守的 **350,000,000 字节 cgroup 上限**和相同 3 小时 wall-time 上限，完整通过 365 天、105,120 个 300 秒步。结果见 `results/v22/remote_annual_pilot_v3_result.json`，逐日资源/耗时见 `results/v22/remote_annual_pilot_v3_progress.jsonl`；前两次中断的逐日记录保留在 `results/v22/remote_annual_pilot_v1_progress.jsonl` 和 `results/v22/remote_annual_pilot_v2_progress.jsonl`。

独立结构审计由 `scripts/v22/audit_annual_runtime_pilot.py` 读取上述文件与合同 v3，核对 365 条连续逐日记录、105,120 步、阶段切换、清理/idle 无新增收获、账本天数与事件成本、28 个有限末状态、进程资源上限；报告和原始文件 SHA-256 见 `results/v22/remote_annual_pilot_v3_audit.json`。这是执行与会计一致性审计，不能替代真实温室轨迹验证。

## 四隔间同步运行与错峰生命周期 pilot（2026-09-28）

固定 2017 年 Cabauw 天气、合同 v3 和示例策略 A/B；四间共用 300 秒时钟，各自持有作物/设施状态、账本和观测，先收齐四间指令，再完成四间物理步进，最后发布端点。此为执行成本和时序检查，不是 LLM episode，也不是实测温室验证。

- 1 天同步短测完成 288 步，66.08 秒，峰值 RSS 137.60 MB。7 天对象观测完成 2,016 步，192.96 秒，峰值 RSS 139.69 MB。改为紧凑数组观测后，7 天完成 193.83 秒，峰值 RSS 135.86 MB；两种存储的四间末状态和资源账逐值相同。对应原始结果在 `configs/v22_remote_four_unit_*day*_result.json`。
- 四间错峰 18 天前缀通过 5,184 个同步步进，480.63 秒，峰值 RSS 153.17 MB。0 号隔间第 14 天停止、第 14–16 天清理、第 16 天重新种植；四间时钟一致，清理期该隔间没有新增收获，Endpoint 只释放已停止作物的汇总。原始结果与逐日记录在 `results/v22/remote_four_unit_annual_prefix18_result.json`、`results/v22/remote_four_unit_annual_prefix18_progress.jsonl`。
- 首次完整四隔间 365 天 pilot 在第 240 天又 218 个 300 秒步（累计 69,338 步）失败：`FloatingPointError: native RHS arithmetic fault: 8`，即 C 浮点溢出标志。耗时 5,488.11 秒、峰值 RSS 220.43 MB，未触及 350 MB/3 小时上限。完整失败结果及前 240 天逐日轨迹分别保存在 `results/v22/remote_four_unit_annual_failed_result.json` 和 `results/v22/remote_four_unit_annual_failed_progress.jsonl`。当前不能声明全年可行或把失败场景剔除；已启动同协议 241 天诊断重放，新增私有故障快照及参考 RHS 对照，待重放结果判断是否为中间溢出误报或实际物理失稳。
