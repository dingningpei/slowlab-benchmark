# Phase 1：四隔间天气闭环与运行门槛

2026-09-27。用户同意主环境采用逐隔间设备容量、中央供应足够的口径。合同 `configs/v22_task_contract_v3.json` 明确中央至少可以同时提供 46.08 kW 供暖、800 mg/s CO₂ 和 25.6 kW 补光电力；这些是由四个逐间上限计算出的**最低充足供应要求**，不是测得的中央设备铭牌，也没有额外的中央争用瓶颈。`slowlab/v22_resources.py` 的独立实现函数验证四间命令集与 [0,1] 范围，逐间保留请求值；GreenLight 各自按锁定设备容量换算为实际通量。合同 v2 保留不改。

`scripts/check_v22_four_unit_weather.py` 在 Cabauw lc1 历史天气下以同一时钟运行四间 active 作物、每间六个 300 秒步。分别提交两套合法政策。每个 tick 先收齐四间 requested，再统一验证 realised，然后四间物理步进完毕才发布新观测。控制器只读已经到达的室内和室外传感器；源天气驱动隐藏模型，不在区间起点给代理。八项公开传感器包括室内温湿度、CO₂、LAI 代理以及累计收获/供暖/补光/CO₂；累计值来自已结算资源账。Full 能读取历史，Endpoint 运行中只能读操作状态。清晨窗口测得的每间最高供暖 120 W/m²、CO₂ 2.0833 mg/m²/s、补光 66.6667 W/m²，均未超过逐间上限。六步检查约 16.76 秒，四间模型各加载一次，峰值 RSS 约 126.9 MB（macOS `ru_maxrss` 字节口径）。证据在 `configs/v22_phase1_four_unit_short_gate.json`。

测试时曾发现非午夜天气起点没有映射到固定 CET 控制时钟，使冬季 06:00 补光错误地关闭。已给控制器与模型共同接入本地时钟偏移，并通过冬季清晨的实际补光/CO₂ 通量及午夜回归。此修复没有引入夏令时；合同仍为固定 CET。

`scripts/check_v22_weather_lifecycle.py` 另对一个隔间执行 300 秒 active→提前停止→两天 576 步 cleanup→重种→300 秒 active，全部使用同一历史天气、时钟、传感器和资源账。提前重种被拒，设施状态跨 empty/active 模式保持，Endpoint 只释放该轮已产生的累计收获、用量和费用；再次重种使用新的 run 编号与新的结算基线。编译 RHS 与缓存解释路径的这条短流程资源账所有比较项差值为零。证据在 `configs/v22_phase1_weather_lifecycle_native_gate.json`。

## 算力门槛仍未通过

编译 RHS 版本短流程总耗时 11.67 秒，其中两模型加载 8.30 秒，两天清理步进 3.36 秒。缓存解释路径旧结果总耗时 36.34 秒。按**空作物清理步进**直接线性外推，四隔间 365 天约 0.68 小时/活动；预算草案的 1,024 活动约 698 单 worker 小时。这个数不是全年实测，也未计成熟作物、模型加载、更多天气文件、LLM、评测器和重试，不能当正式预算。详见 `configs/v22_phase1_dynamic_runtime_projection.json`。

Phase 1 的“可持续推进”计算门槛目前仍未过：单机 MacBook 上启动全年四隔间或大矩阵，会占用过长时间。下一步应先 profile 编译路径的每步求解、DataFrame/全辅助输出、逐步传感器和历史查询开销；在保持 300 秒控制与观测、原方程/容差、资源积分及因果检查的前提下找等价加速。优化后再运行短轨迹逐状态/账本回归与一个正式全年 pilot。不要把这次两天 empty-crop 外推称为成熟作物全年验证。

尚未完成四隔间跨生命周期正式调度、公共 API 硬隔离、传感器噪声、全年天气分区/长期数值稳定、成熟作物结算及真实温室轨迹验证。没有新数据下载或 LLM API 调用。
