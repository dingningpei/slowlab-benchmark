# Phase 1：四隔间共享容量合同缺口

`configs/v22_task_contract_v2.json` 为每个 96 m² 隔间指定供暖 11.52 kW、CO₂ 200 mg/s、补光电力 6.4 kW。四隔间各自达到上限时，合计分别为 46.08 kW、800 mg/s、25.6 kW。屋顶通风开口是逐隔间几何量，不宜当作中央共享执行器。

合同没有中央锅炉、CO₂ 分配管网或总配电容量，也没有竞争时的分配规则。因此当前单隔间烟测中 `requested=realised` 合理，但不能宣称实现了四隔间共享设备限流。见 `configs/v22_shared_capacity_gap_audit.json` 的机器审计。

可行口径：

1. **独立隔间容量、中央供应充足**：四个隔间各受原单隔间上限约束；中央设施至少能同时供给四个上限，不引入未经证实的争用。场地和日历预算仍共享。论文称“多隔间、逐隔间设备容量”，不称“共享锅炉瓶颈”。
2. **显式合成中央瓶颈**：另行冻结总供暖/CO₂/电力容量，以及确定性的公平分配规则；记录每个 tick 的请求、实际值、被限流量与原因，并把实际值送入 GreenLight。此口径能研究设备竞争，但容量数值不能冒称 AGC 实测。

**推荐第一种**作为主环境，因为现有证据只支持逐隔间上限；把第二种留作事前定义的容量敏感性实验。变更合同必须出新版本，不能在当前 v2 下无声添加中央瓶颈。这个口径选择决定四隔间调度和结果，故 Phase 1 的完整执行器暂不实现共享限流。
