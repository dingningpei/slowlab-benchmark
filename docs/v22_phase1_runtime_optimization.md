# Phase 1：不改变控制/观测协议的运行优化

2026-09-28。目标是处理 `docs/v22_phase1_four_unit_weather_and_runtime.md` 指出的计算门槛；没有缩短作物周期、放宽 ODE 容差或延长 300 秒控制/观测间隔。原编译 RHS、天气驱动两天清理流程的 576 个 empty 步耗时 3.360 秒。profile 显示模型初次加载很慢，但与全年步进相比只付一次；步进中主要开销为 LSODA 求解、每步 pandas 全输出打包及控制器对历史记录的重复全表扫描。

第一项优化给 `OnlineObservations` 建立按隔间和变量的测量时间索引。`latest()` 用二分定位，仍按 `available_at` 拒绝尚未送达的记录；历史查询仍保留原时间和乱序送达语义。已有延迟、乱序、历史 cutoff 和不可变性测试通过。相同两天流程的步进测得 2.841 秒；短基准有运行波动，不能把单次差值当作全年加速比。

第二项为显式可选的 `array_output`：保留所有原方程、所有辅助量的求值、LSODA、容差、求解时间点和非有限检查，仅在 executor 内部跳过每 300 秒一次的 pandas DataFrame 打包，用等长 NumPy 数组交给传感器和账本。空作物常量通量标量按原 pandas 行为广播到时间网格。默认 DataFrame 路径不变。连续新旧配对运行得到 frame 3.010 秒、array 2.471 秒。28 个最终物理状态最大绝对差 0，资源账逐项完全一致；见 `configs/v22_phase1_optimization_audit.json`。这只验证该两天短轨迹，尚未覆盖成熟作物和全年数值敏感性。

按最快短轨迹的**空作物**步速机械外推，四隔间 365 天约 0.50 单机小时，预算草案的 1,024 场约 513 worker-hours。此数既不是成熟作物全年实测，也不含模型加载、LLM/BO、评测与重试。它依然远超在一台 MacBook 上直接跑正式矩阵的合理负担。

下一道 Phase 1 门槛应是：先用同等协议的成熟作物多日窗口和至少一场全年 pilot 测真实壁钟时间、峰值内存、状态/账本数值一致性；然后依据正式方差与计算预算冻结 site/campaign 数，并选择远程并行资源。不得仅因为旧草案列了 1,024 场就启动计算。若全年 pilot 仍过重，先评估保持物理轨迹等价的内核级加速；任何改变观测频率或作物周期的方案都须另版合同和实验解释。

## 早期活作物窗口交叉检查

另用 `scripts/check_v22_active_weather_window.py` 跑单隔间 2017 年初连续七天（2016 个 300 秒步），两条路径使用相同天气、控制器、八项公开观测和账本。frame 步进 9.613 秒，array 步进 8.235 秒；28 个末状态最大绝对差为 0，资源账完全一致。按 array 的**早期**作物速度机械外推，四间全年约 0.48 小时，草案 1,024 场约 489 worker-hours。它与两天空作物外推同量级，但仍不能代替成熟作物或全年实测。证据在 `configs/v22_phase1_active_7d_runtime_audit.json`。

阶段决定：当前改动可保留为默认关闭的可选加速路径；下一步先用可承受的成熟作物窗口和单场全年 pilot 核算准确壁钟与内存。正式样本量必须由 pilot 方差/所需精度和算力预算共同冻结，正式矩阵应在经过同轨迹回归的远程并行环境运行；用户此前反映 MacBook 风扇噪声，不能把数百单机小时直接交给本机。
